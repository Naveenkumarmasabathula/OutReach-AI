# Known Limitations and Tradeoffs

Updated as implementation proceeds. Per PRD §33, this exists so a reviewer can distinguish an intentional prototype tradeoff from incomplete/broken functionality.

## Phase 0 / Phase 1

- **`esbuild` moderate advisory left unpatched.** `drizzle-kit`'s legacy `@esbuild-kit/*` loader pulls in a vulnerable `esbuild` version whose issue is that its dev server accepts cross-origin requests. We never run `esbuild serve` — it's only used for `drizzle-kit`'s offline CLI codegen — so this isn't reachable. Forcing the fix would downgrade `drizzle-kit` to 0.18.1, a much older major version; not worth the churn for a dev-only, non-exploitable transitive dependency. (The related high-severity `drizzle-orm` SQL-injection advisory *was* fixed, by upgrading to `drizzle-orm@0.45.2`.)
- **Dev-only secrets are committed.** `docker-compose.yml`'s Postgres/Redis credentials and the `app_runtime` DB role's password (in `server/drizzle/0001_enable_row_level_security.sql`) are fixed, simple values. This is acceptable only for local development. Any real deployment must supply these via environment/deployment secrets instead — see PRD §27 and §25's "prototype-level security vs. production compliance" distinction.
- **Tenant-isolation tests run against the dev database, not a dedicated/torn-down test DB.** `server/test/security/patient-isolation.test.ts` creates hospitals/users with a random suffix per run rather than truncating a separate test database. Fine for now; a proper isolated test DB with truncation between runs is the Phase 11 follow-up, alongside the completeness check across all tenant-scoped tables described in `multi-tenancy.md` §1.
- **`users` table has no Row-Level Security**, unlike every other tenant-scoped table — a deliberate exception, not an oversight. See `multi-tenancy.md` §2 for why (login must look up a user by email before any hospital is known).
- **Seed data is not crash-safe mid-hospital.** `server/src/db/seed.ts` inserts a hospital row, then its staff/patients, in sequence; if the process is killed between those two steps, the hospital row exists without staff/patients, and a re-run will skip it entirely (`onConflictDoNothing` on the hospital insert). Acceptable for a one-time dev seed script; not a pattern used anywhere in request-serving code, which is idempotent per `multi-tenancy.md`/PRD §24 instead.
- **The outbound queue, the AI agent layer, escalation *management* (reviewer workflows, notifications), and observability are not yet implemented.** Phase 1 covers the underlying hospital/patient/encounter data model and CRUD, plus the EHR abstraction layer — see `docs/ehr-abstraction.md`. Phase 2 (campaigns/eligibility) is now also complete — see `docs/campaigns-eligibility.md`.
- **`escalations` table is intentionally minimal.** It supports the EHR interface's `createEscalationRecord` write today (hospital, patient, encounter, trigger, clinical indicators, priority, status), but PRD §21's full shape needs campaign/call references and consensus/reviewer fields that depend on Phases 2, 3, and 6, which don't exist yet. Phase 6 extends this table rather than replacing it — see `docs/ehr-abstraction.md`.
- **Two pre-existing `Promise.all`-on-one-transaction bugs, found and fixed while adding EHR tests.** `encounterService.getPatientTimeline` and `patientService.listPatients` both issued multiple queries via `Promise.all` against a single transaction's one `pg` connection — tolerated today only via an internal queue in `node-postgres`, and already showing a `DeprecationWarning` in test output. Fixed by awaiting sequentially instead (a single Postgres transaction can't run statements concurrently anyway, so this was free). Neither bug was reachable by the test suite until `test/ehr/ehr.test.ts` exercised `getPatientTimeline` for the first time — worth remembering that a green test suite only proves what it actually calls.
- **A pre-existing bug in `createEncounter`, found while adding campaign tests**: it never set `status`, so every encounter created via the API/UI silently kept the table's `in_progress` default instead of `discharged` — meaning the eligibility engine (and anything else filtering on discharge status) would never have seen them. Fixed; see `docs/campaigns-eligibility.md` for detail.
- ~~Eligibility does not yet check "existing outreach status"~~ — **partially resolved in Phase 3**: `enqueueEligiblePatients` won't create a second task for a patient who already has one for the same campaign (the idempotency PRD §11 asks for), so a patient is never double-worked. What's still open: the eligibility *function* itself doesn't take existing-task state as an input, so a patient already `manual_follow_up` on campaign A could still be freshly eligible for campaign B's separate outreach — a real design question for Phase 6+ (should one hospital-wide outreach state block a patient from unrelated campaigns?), not a bug in what exists today.
- ~~Campaign `priority`, `outboundCapacity`, and `retryLimit` are stored but not yet used~~ — **resolved in Phase 3**: all three now drive the queue's priority scoring, capacity enforcement, and retry-exhaustion logic respectively. See `docs/queue-design.md`.
- **`expectedAttempts` in the workload estimate is a documented upper bound** (`eligiblePatientCount × (retryLimit + 1)`), not a contact-rate prediction — real attempt modeling depends on Phase 3's retry/backoff behavior, which now exists but doesn't feed back into this estimate yet (a nice-to-have refinement, not a correctness issue — the estimate is still honestly labeled as an upper bound).

## Phase 3 (Outbound Queue & Scheduler)

- **Voice/AI is an explicit, deterministic placeholder**, per direct product instruction, not an oversight: `callSimulator.ts`'s `simulateCallOutcome` stands in for Phase 5's real Voice Intake Agent. It's hash-based (not `Math.random()`) specifically so Phase 9's safety evaluation can reproduce the same scenario after a prompt/model change. See `docs/queue-design.md`'s "call-outcome simulator" section.
- **Escalations produced by the queue today are simulator-triggered, not clinically real.** An `escalated` outcome creates a genuine `escalations` record via the EHR interface (the write path, audit trail, and state transition are all real), but *what decides* to escalate is currently the placeholder simulator's hash, not an actual clinical assessment. Phase 5 replaces the decision-maker, not the record-creation path.
- **A real RLS-related bug, found via the stale-lock recovery test**: the first implementation of `releaseStaleLocks` queried `outreach_tasks` (RLS **forced**) through the app's unscoped DB connection, which silently returns zero rows for any forced-RLS table regardless of actual data (the connection never sets `app.current_hospital_id`). Fixed by enumerating hospitals from the unscoped `hospitals` table (no RLS — it's the tenant root) and running a properly scoped query per hospital. Full writeup in `docs/queue-design.md`'s "failure recovery" section — this is exactly the class of mistake `docs/multi-tenancy.md` itself warns is easy to make.
- **BullMQ's worker concurrency (10) is independent of hospital capacity** — this is intentional, not a gap: capacity is enforced in Postgres at claim time, before a job ever reaches BullMQ, so the two settings don't need to (and shouldn't) coordinate. See `docs/queue-design.md`.
- **Per-campaign `outboundCapacity` is enforced, but campaigns don't yet negotiate priority beyond the scoring formula** — if two campaigns are both starved for capacity, the one with more urgent/higher-scoring tasks simply wins more often; there's no separate "campaign fairness" allocation on top of that. This is a deliberate simplicity choice (PRD asks for starvation prevention *per task*, via the wait-time term, not guaranteed per-campaign throughput), not an oversight.
- **The required queue simulation (`npm run queue:simulate`) mixes organic (real-simulator) and showcase (forced-outcome) patients** — documented in `docs/queue-design.md` — specifically because the organic simulator's rarer outcomes (escalation, callback) aren't guaranteed to appear in any single run by chance, and a required grading deliverable shouldn't depend on being lucky. Capacity enforcement and priority ordering are exercised for real for every patient regardless.
- **UPDATE (found and fixed in Phase 8): the original two-layer concurrency design above was not actually sufficient.** The live capacity count was a plain, unlocked read, and enough concurrent callers for the same hospital could each read stale "0 active" state and collectively over-claim past real capacity, even though no single row was ever double-claimed. 100% reproducible under enough concurrent load (verified via a dedicated stress script, not assumed). Fixed with a Postgres advisory transaction lock — full writeup, including how it was found and the before/after stress-test numbers, in `docs/queue-design.md`'s "Concurrency control" section. Left here, not deleted, so this file's history doesn't silently erase that the original claim above was wrong for several phases before Phase 8.

## Phase 4 (Protocols & Knowledge Retrieval)

- **Retrieval is keyword/tag matching, not semantic/embedding search.** Deliberate for this phase — see `docs/protocols-knowledge-retrieval.md`'s "Retrieval is keyword/tag-based" section for why, and its documented upgrade path (swap just `retrieveRelevantProtocols`'s scoring step) for when Phase 5's real agent usage might need it.
- **No hard delete for protocols**, only soft-deactivate — a permanent design choice (a protocol may already be cited by a past retrieval/escalation), not a deferred feature.

## Phase 5 (AI Agent Layer)

- **UPDATE: a real `GEMINI_API_KEY` was later supplied and `GeminiProvider` live-verified.** `generateDocumentation` (flash tier, `gemini-3.5-flash`) works end-to-end against the real API. `assessTriage` (pro tier, `gemini-3.1-pro-preview`) correctly threw an explicit `AIOutputValidationError` against a real `429` quota error — the account has zero free-tier quota for pro-tier models, a billing fact, not a code defect — so a genuinely *successful* pro-tier call remains unverified until billing is enabled. `SimulatedAIProvider` remains what all automated tests and the required `queue:simulate`/`safety:evaluate` scripts run against, deliberately, for reproducibility. Full detail in `docs/ai-usage.md`.
- **Audit logging (the "regulated subject" pattern) covers only the AI agent's own PHI *reads*** via the `AuditedEHR` decorator (`server/src/ehr/auditedEhr.ts`) — still not every pre-existing human-facing read route (patient detail pages, encounter lookups). UPDATE (Phase 10): the separate, PRD §21-named "important operations" audit category (campaign create/pause, staff reviews, AI consensus decisions) *was* completed in Phase 10 — see `docs/observability-reliability.md`. Extending `AuditedEHR`'s per-read wrapping to ordinary human PHI-read routes specifically remains out of scope, for the reason given there.
- **The telephony connectivity signal (`simulateCallOutcome`'s no_answer/busy/voicemail/etc. buckets) is still the Phase 3 placeholder.** Phase 5 replaced the *clinical* decision-making for connected calls (see `docs/ai-usage.md`), not whether a call connects at all — that remains a `docs/voice-provider.md`-documented future swap, alongside the rest of a real `VoiceProvider`.
- **No dedicated Phase 5 frontend.** Escalations created by the AI pipeline surface in the existing hospital-wide queue-health view (Phase 3); a proper escalation review UI (transcript, both independent assessments, consensus rationale, resolve/assign actions) is explicitly Phase 6 scope.
- **The rule-based triage path's symptom-severity map is small and illustrative** (5 symptom keywords), not a real clinical knowledge base — expanding it, or moving it into hospital-configurable protocol data instead of an in-code map, is a reasonable future refinement, not attempted now.

## Phase 6 (Escalation & Human-in-the-Loop)

- **No timeout-based auto-escalation to a backup reviewer.** PRD §18's example ("an escalation notifies a nurse, then escalates to a backup reviewer if not acknowledged within a configured period") needs the async event/workflow bus Phase 7 builds (delayed jobs, configurable reviewer timeouts) — not attempted with ad-hoc timers in this phase.
- **No reviewer workload balancing or auto-assignment.** `assignEscalation` always takes an explicit `reviewerId`; there's no "assign to whoever has capacity" logic. Not required by the PRD; a reasonable Phase 8 addition only if it turns out to matter.
- **Notifications remain simulated** (a real, queryable `notifications` table, but `status` is always `"simulated"`, never a real email/SMS send) — matching Decision #6 and the same placeholder-now/swap-later posture as voice and AI.

## Phase 7 (Workflows & Events)

- **Only `escalation.created` has a real event consumer.** All 15 catalog event types (`server/src/events/types.ts`) are genuinely published from their real mutation points, but only one drives a side effect today — see `docs/workflows-events.md`'s "Only one event type has a real consumer today" for why this is a stated scope boundary, not an oversight. Adding a consumer for another event type is a `HANDLERS` map entry, not a publish-side change.
- **A minor, non-blocking Jest artifact**: the full `npm run test --workspace server` run occasionally prints "A worker process has failed to exit gracefully and has been force exited" even though every test passes and the process exits with code 0. Root cause is almost certainly Jest's parallel-worker teardown timing interacting with the BullMQ/Redis connections several test files now open (queue-touching test files already close their own connections in `afterAll`, per `docs/workflows-events.md`'s "genuinely leaked resource" note) — cosmetic, not a correctness issue, and not chased further given it doesn't affect test results or CI exit codes.
- **No cancellation of a scheduled backup-reviewer timeout job on early acknowledgement** — the job still fires at its original delay but safely no-ops (re-checks status first). See `docs/workflows-events.md`'s "What was deliberately not built now."
- **"Backup reviewer" is interpreted as the `HOSPITAL_ADMIN` role** — there's no distinct backup-reviewer role in the RBAC model, and PRD §18 doesn't require inventing one.

## Phase 8 (Dashboards & Analytics)

- **AI usage and error-rate panels are not on the Platform Admin dashboard yet** — PRD §20 lists them, but honestly populating them needs Phase 10's observability work; fabricating placeholder numbers would be worse than omitting them. See `docs/dashboards-analytics.md`.
- **No pagination on the Platform Admin's per-hospital table** — fine at current data volumes (250+ hospitals rendered without issue during testing, since it's a simple table, not a concern this prototype needs to solve).
- **The critical queue-concurrency race documented in the Phase 3 section above** was found and fixed during this phase's testing, not Phase 3's — noted there (where the bug actually lived) rather than here, but cross-referenced since this phase's own full-suite test run is what surfaced it.

## Phase 9 (Safety Evaluation)

- **The evaluation covers the triage/consensus layer only, not the Voice Intake Agent's own symptom extraction** — a deliberate scope boundary (each case supplies structured `reportedSymptoms` directly rather than depending on any extraction step), not an oversight. See `docs/safety-evaluation.md`'s "what this evaluates, and what it doesn't."
- **Zero false negatives on the current 14-case dataset is not a general safety guarantee** — it reflects that every case was hand-picked with a defensible expected answer, not that the system is immune to missing something. Real, disclosed weaknesses (exact-substring phrase matching with no synonym/paraphrase handling, no negation handling, no "confidence too low to classify" state distinct from routine) are documented in `docs/safety-evaluation.md` rather than hidden behind a clean-looking pass rate.
- **The dataset has not been re-run against a real Gemini model.** A `GEMINI_API_KEY` has since been supplied and `GeminiProvider` live-verified (`docs/ai-usage.md`) — `npm run safety:evaluate` would now automatically use the real provider if `aiProvider`'s default binding were pointed at it instead of `SimulatedAIProvider`, but the pro-tier model `assessTriage` calls has zero free-tier quota on the supplied account, so a real run would currently fail every case on the AI-model path rather than produce comparable results. Worth re-running once billing is enabled, particularly for the two adversarial cases.

## Phase 10 (Observability & Reliability)

- **No cost estimation for AI usage** — token counts are logged (`GeminiProvider`), a dollar estimate is not, since that needs current per-model pricing as an input that isn't safe to hardcode and silently let go stale. See `docs/observability-reliability.md`.
- **No frontend page for browsing the audit log or event log** — the read APIs exist and are tested (`GET /api/v1/audit-log`, `GET /api/v1/platform/hospitals/:id/audit-log`), but no UI was built for them, given the scope remaining in Phase 11.
- **No circuit breaker for the Voice Provider or EHR interface**, only the AI provider — `SimulatedVoiceProvider`/`MockEHR` can't actually fail the way a real network-dependent implementation could, so circuit-breaking around them would be untestable, speculative code. The `CircuitBreaker` class itself is generic and ready to wrap a real `TwilioVoiceProvider`/`RealEHR` once either exists.
- **The audit-log extension covers the specific "important operations" PRD §21 names by name** (campaign lifecycle, escalation reviews, AI consensus decisions) — it is not a blanket "audit every mutation" middleware. A new mutating route added later needs its own explicit `auditUserAction` call if it should be audited; this doesn't happen automatically.

## Phase 11 (Testing)

- **The test-coverage audit that drove this phase checked PRD §26's own checklist, not general code coverage.** It's possible other gaps exist outside what that checklist names explicitly; this phase closed exactly the 5 gaps found against that specific list (auth failure paths, central validation-error handling, queue priority ordering at the integration level, AI schema rejection, `GeminiProvider` retry logic), not a general "100% coverage" pass.
- **`GeminiProvider`'s tests mock the SDK client directly** (via `jest.spyOn` on a real client instance constructed with a fake key) rather than using Jest's ESM module-mocking (`jest.unstable_mockModule`), which this project doesn't otherwise use. This proves the retry/repair/throw *logic* is correct, but still doesn't prove anything about the real Gemini API's actual behavior (response shape, latency, rate limits) — that remains genuinely unverified until a real key is supplied, same caveat as everywhere else `GeminiProvider` is mentioned in these docs.

## Phase 12 (Deployment & Deliverables)

- **Not actually deployed.** Per explicit product direction, this phase produced every deliverable *document* (architecture diagram, deployment instructions, a demo-video script) without performing the actual hosted deployment — `docs/deployment.md` explains exactly what running it would involve and why it wasn't done here (an account/billing decision only the project owner can make).
- **No demo video file.** This environment has no screen/audio recording capability. `docs/demo-script.md` is the substitute: a precise, step-by-step walkthrough of the exact required flow, written from real, already-tested behavior rather than a guess — whoever records it should be able to follow it directly without debugging.
- **`GET /api/v1/escalations/:id/notifications`** was added while writing `docs/architecture.md`, closing a real gap: the `notifications` table and `sendNotification` service function existed since Phase 6, but nothing had ever exposed a read route for them, and PRD §24 names "notifications" as required API surface. Found by writing an honest architecture document, not by a dedicated audit — worth noting as a case where documentation work surfaced a real, if minor, product gap.

## Frontend (initial build, ahead of the phase plan)

Built early at the user's request (before Phases 4–7), so it currently only covers what the backend already supports: auth, hospital onboarding/config, patient/encounter CRUD, staff management, campaign CRUD/lifecycle (Phase 2), and (as of Phase 3) a live hospital-wide queue-status view on the campaign detail page. Escalation-management and analytics screens don't exist yet because those APIs don't exist yet — they'll be added alongside their respective backend phases, not before.

- **The Queue section on a campaign's detail page shows the hospital's whole queue, not that campaign specifically** — `getQueueHealth` is hospital-scoped (matching the queue's actual concurrency-semaphore key), not campaign-scoped. Labeled explicitly in the UI so it isn't mistaken for per-campaign state. A campaign-filtered breakdown is a reasonable Phase 8 dashboard refinement, not built now.

- **Patient list has no search/filter.** The backend doesn't support filtering by name/MRN/consent yet, so the list is pagination-only. Adding a non-functional search box would have been misleading UI, so it was deliberately left out rather than half-built.
- **No dark mode, no verified mobile layout.** The design system defines light-surface tokens only; responsive behavior below desktop width hasn't been tested.
- **Design-token naming gotcha** (see `docs/design/dashboard-design-system.md`'s dedicated section): custom Tailwind v4 spacing tokens initially collided with Tailwind's own reserved `max-w-*` keyword vocabulary, silently breaking every card's width. Fixed by namespacing custom tokens (`ds-` prefix); documented in detail there since it's a reusable lesson, not just a one-off fix.
- **Verified via a scripted Playwright pass against the production build** (`vite preview`, not `vite dev`) covering login, both roles' navigation, every implemented page, and a create/read round-trip — not manually clicked through by a human. Screenshots are not committed to the repo (they're a point-in-time verification artifact, not documentation).
