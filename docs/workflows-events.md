# Workflows & Events (Phase 7, PRD §18)

## What this covers

An asynchronous, idempotent event bus for the platform's "important events," and one concrete multi-step workflow built on top of it end-to-end: an escalation notifies every clinical reviewer immediately, then — if nobody has acknowledged it within a hospital-configurable timeout — escalates itself to backup review (bumped priority, a notification to hospital admins), exactly PRD §18's own worked example.

## Design

**Built on the existing BullMQ+Redis infrastructure, not a new message broker.** The tech stack is intentionally open per the PRD, and this project already has a proven, tested async-job layer from Phase 3 (`queueService`/`worker.ts`). Adding a second kind of async work (events) on the same infrastructure was far cheaper than introducing a new pub/sub technology, and reuses patterns already established: `jobId`-based dedup (matching `worker.ts`'s `jobId: task.id` for outreach calls), a dedicated `Worker` per queue, graceful shutdown on `SIGINT`/`SIGTERM`.

**The durable write happens before the async enqueue, not instead of it.** `publishEvent` (`server/src/events/publish.ts`) inserts an `app_events` row first, then enqueues a BullMQ job referencing it. If Redis is briefly unavailable at publish time, the event still exists in Postgres and can be replayed — the row is the source of truth, the job is only the delivery mechanism. This mirrors `docs/queue-design.md`'s own "Postgres reserves capacity, BullMQ only distributes already-reserved work" split.

**Idempotency has two independent layers**, per PRD §18's "must tolerate duplicate events, retries... important operations must be idempotent":

1. BullMQ's own `jobId` dedup (the job for a given event can't be double-enqueued).
2. The consumer's own `processedAt` check (`server/src/events/consumer.ts`) — set only after a handler completes successfully, checked before dispatching. A redelivered job (BullMQ's own retry after a transient failure, or a manual replay of the same `eventId`) is always a safe no-op once `processedAt` is set.

The same two-layer pattern is reused for the backup-reviewer timeout job itself: `jobId: `escalation-timeout-${escalationId}`` (BullMQ rejects `:` in custom job IDs — a real bug caught by the test suite, not assumed away, see "bugs found" below) plus `checkEscalationTimeout`'s own re-check of the escalation's *current* status before acting, so firing it twice (or firing it after the escalation was already acknowledged through a completely different path) is always safe.

**Two event types have a real consumer today** — `EVENT_TYPES` (`server/src/events/types.ts`) lists all of PRD §18's "important events" (campaign lifecycle, task completion/failure, retries, callbacks, escalation lifecycle), and every one of them is genuinely published from its real mutation point — `campaignService`'s lifecycle functions, `queueService.recordAttemptOutcome`'s outcome switch, `escalationService`'s acknowledge/resolve. `dispatchEvent`'s handler map (`server/src/events/handlers.ts`) registers `escalation.created` (PRD §18's spelled-out multi-step workflow: notify every `CLINICAL_REVIEWER`, then escalate to a backup reviewer if unacknowledged within a configurable timeout) and `task.manual_follow_up` (notifies every `CAMPAIGN_MANAGER`/`HOSPITAL_ADMIN` at the hospital when a task exhausts its retries — previously the task/record existed with nothing paging a human about it; see `docs/queue-design.md`'s "Manual-follow-up notification" section for that fix). Every other event type is persisted (so it's audit-visible, queryable, and a future consumer could be added without touching the publish side at all) but doesn't yet drive a side effect — logged at debug level as "no registered consumer yet" rather than silently doing nothing.

**The reviewer timeout is hospital-configurable without touching AI logic** (PRD §18: "non-engineering users should be able to configure operational behavior... without changing AI logic"). Rather than a new configuration system, it reuses `hospitals.settings` — a jsonb column that already existed since Phase 0, already documented as covering exactly this kind of hospital preference, and already exposed through the existing hospital-config update endpoint and Settings page. `getEscalationReviewerTimeoutMinutes` (`hospitalService.ts`) reads it with a sensible default (30 minutes) so a hospital that's never touched this setting still behaves correctly.

**"Backup reviewer" is interpreted as the `HOSPITAL_ADMIN` role**, since the RBAC model (`server/src/config/roles.ts`) has no distinct "backup reviewer" role and inventing one for this single workflow would have been scope creep beyond what PRD §18 actually asks for (detect-and-escalate-on-timeout, not a new organizational hierarchy). Documented here as an explicit interpretation, not left implicit.

## What was verified

- `tsc --noEmit` on both `server` and `web`; `npm run build --workspace web`.
- RLS confirmed via `psql` on the new `app_events` table.
- A real bug caught by the test suite before it shipped: BullMQ rejects `:` in a custom `jobId` (`Custom Id cannot contain :`) — the first draft used `escalation-timeout:${escalationId}`, which failed immediately with a real error, not a silent misbehavior. Fixed to `escalation-timeout-${escalationId}`.
- New test suite (`server/test/events/events.test.ts`, 4 assertions): `publishEvent`/`processEvent` round-trip and idempotency (processing an already-processed event is a safe no-op), the `escalation.created` handler actually creating notification rows for every `CLINICAL_REVIEWER` and actually scheduling a real, inspectable BullMQ delayed job, and `checkEscalationTimeout`'s two branches (still-open escalations get bumped priority + admin notification; already-acknowledged escalations are untouched). Full suite: 92/92 passing (was 88 before this phase).
- A genuinely leaked resource, found by running the full suite rather than individual files: `campaignService`/`queueService`/`escalationService` now transitively construct BullMQ `Queue` instances (via `events/publish.ts`) at module load, and none of the test files that exercise them were closing those connections — Jest hung indefinitely rather than exiting. Fixed by having each affected test file's `afterAll` close every queue plus the shared Redis connection, the same discipline those files already applied to the Postgres pool.
- Live smoke test: started the real dev server *and* the real background worker process (not a direct function call), created a real escalation against the demo `Riverside General` hospital via a small one-off script, and watched the actual running worker consume the `escalation.created` job asynchronously from Redis — its structured log line shows a real notification created for the real seeded `CLINICAL_REVIEWER` user, and `redis-cli KEYS` confirms a real delayed `escalation-timeout-*` job was scheduled. This is the one thing a unit or direct-function-call test can't prove: that the actual background worker process, not just the underlying functions, drives this workflow end-to-end.

## What was deliberately not built now

- **Consumers for the other 13 published event types** — see "Two event types have a real consumer today" above. Adding one is now just a `HANDLERS` map entry; the publish side needs no changes.
- **A dedicated events/notifications frontend page** — notifications already surface implicitly (the escalation review UI shows escalations; a human checking `GET /api/v1/escalations` sees the effect of the workflow). A raw event-log viewer is reasonable Phase 8/10 (dashboards/observability) territory if it's ever needed.
- **Cancelling a scheduled timeout job when its escalation is acknowledged early.** The job still fires at its original delay either way — it's just a cheap no-op once it re-checks status. Actively removing the BullMQ job on acknowledgement would save a little Redis housekeeping but adds real complexity (tracking/removing jobs from two different services) for no behavioral difference a user would ever observe.
