# Deployment (Phase 12)

**Status: documented, not executed.** This describes exactly how to deploy the platform to a public host; actually doing so (and producing a live URL) is a separate step left to the project owner, since it requires an account/billing decision on a hosting platform and a real domain/URL to publish. A real `GEMINI_API_KEY` is now available and live-verified (`docs/ai-usage.md`) — the deployed API/worker services just need it set as an env var like any other secret. Note the flash-tier model works on the supplied key's current (free-tier) plan; the pro-tier model used for clinical triage does not until billing is enabled on the associated Google Cloud project — see `docs/ai-usage.md` for what that means operationally (the circuit breaker degrades gracefully rather than failing outright). Nothing about the application itself is blocked on any of this: every service is already containerizable and configured entirely through environment variables (PRD §27: "secrets must be supplied through environment/deployment configuration and never committed to source control" — already true today, see `server/.env.example`).

## What needs to run

Five independent processes, matching `docs/implementation-plan.md`'s Deploy row:

| Process | Command | Notes |
|---|---|---|
| PostgreSQL | managed by the host | Needs two roles: a superuser/owner (migrations) and `app_runtime` (the app itself) — see `docs/multi-tenancy.md` §2 for why both are required |
| Redis | managed by the host | BullMQ's queue backend |
| API | `npm run build --workspace server && npm run start --workspace server` | Express 5, stateless — safe to run multiple instances behind a load balancer if the host supports it |
| Worker | `npm run build --workspace server && npm run worker --workspace server` | Must run as its own long-lived process, separate from the API — see `server/src/worker.ts`. Also stateless; running more than one instance is safe (the queue's concurrency-safety guarantees, `docs/queue-design.md`, hold across multiple worker processes, not just multiple threads in one) |
| Web | `npm run build --workspace web` then serve `web/dist/` as static files | A Vite production build — any static host (the API host's own static-file serving, or a CDN) works; it only needs the API's public URL configured (see below) |

## Recommended hosts

**Railway or Render**, per `docs/implementation-plan.md`'s original choice — both support "one service per process" deployment (a Postgres addon, a Redis addon, and one service each for API/worker/web) without needing a custom orchestration layer, which fits a prototype's constraints (PRD §27: "justify choices based on reliability, development speed, scalability, maintainability, safety, and prototype constraints") better than standing up Kubernetes or a hand-rolled VM setup for something at this stage. Either platform's free/low tiers are enough to run all five processes for an evaluation deployment; neither choice is load-bearing for the application code itself (nothing here is Railway- or Render-specific) — moving to a different host later only means recreating the same five services elsewhere.

## Step-by-step (applies to either host; adjust exact UI clicks per platform)

1. **Provision Postgres and Redis** as managed add-ons/services on the chosen host. Note their connection strings.
2. **Create the `app_runtime` role** by running `server/drizzle/0001_enable_row_level_security.sql`'s role-creation statement against the new database (or simply run the full migration set — step 4 — which creates it as part of migration 0001). Use a real generated password, not the dev default in `docker-compose.yml`.
3. **Set environment variables** on the API and worker services (both need the same set — see `server/.env.example` for the full list): `DATABASE_URL` (as the `app_runtime` role, never the superuser — this is the single most important thing to get right, per `docs/multi-tenancy.md` §2's "Postgres superusers bypass RLS unconditionally" warning), `MIGRATE_DATABASE_URL` (the superuser connection, needed only for the one-time migration step below — some hosts let you run this as a one-off job instead of setting it as a persistent env var), `REDIS_URL`, `JWT_SECRET` (generate a real random secret — never reuse `dev-only-change-me`), `JWT_EXPIRES_IN`, `PORT`, `GEMINI_API_KEY` (optional — leave unset to keep running the simulated AI provider; set it to activate `GeminiProvider`, per `docs/ai-usage.md`).
4. **Run migrations once**, using `MIGRATE_DATABASE_URL`: `npm run db:migrate --workspace server`. This creates every table, RLS policy, and the `app_runtime` role itself. Note: as of the reliability-audit follow-up, the five `idempotency_key` columns (`communications`/`tasks`/`escalations`/`notifications`/`observations`) and their unique indexes exist in the Drizzle schema (`server/src/db/schema/*.ts`) but, due to a migration-folder conflict with concurrent work at the time (see `docs/observability-reliability.md`'s "What's still not done after this pass"), were applied directly to the dev database rather than through a committed migration file — a fresh deployment's `db:migrate` run should be preceded by generating and committing that migration (`npm run db:generate --workspace server`), or those five columns won't exist on a brand-new database.
5. **Seed demo data** (optional but recommended for an evaluator-facing deployment): `npm run db:seed --workspace server`. This creates the three demo hospitals and their staff/patient data described in the top-level `README.md`'s demo credentials table — as of the reliability-audit follow-up (`docs/observability-reliability.md`'s Fix #7), this also includes a deterministic outreach history (a mix of completed/no-answer/busy/dropped/callback/escalated outcomes, plus a few `manual_follow_up` tasks and real escalations) and medications/procedures per patient, so the demo data alone already shows this variation before any live campaign runs.
6. **Deploy the API and worker** as their own services, each running the build+start commands from the table above, both pointed at the same Postgres/Redis.
7. **Deploy the web build**, setting `VITE_API_BASE_URL` (read in `web/src/lib/api.ts`) to the API service's public URL at build time. Locally this is unset and requests go through `web/vite.config.ts`'s dev-server proxy instead (`/api` → `http://localhost:4000`) — production has no such proxy, so the built frontend needs the real API URL baked in via this env var before running `npm run build --workspace web`.
8. **Verify**: hit `GET /health` on the deployed API (see `docs/observability-reliability.md`) and confirm `{"status": "healthy"}`; log into the web app with the seeded demo credentials; run through the demo script (`docs/demo-script.md`) end to end against the live deployment before sharing the URL.

## What changes about the application's own behavior when deployed vs. local

Nothing. There is no separate "production mode" branch anywhere in the codebase beyond `NODE_ENV` (used only for a couple of Express defaults like error verbosity) — the same Express app, the same Drizzle schema, the same BullMQ setup, and the same RLS policies run identically in Docker Compose locally and on a hosted platform. This was a deliberate design goal throughout: every phase's local verification (curl smoke tests, Playwright browser passes, the required queue simulation and safety evaluation scripts) is evidence for the hosted deployment too, not just the dev environment, because nothing behaves differently between the two.

## Before using this with real patient data

See `docs/known-limitations.md`'s running list of prototype-level tradeoffs (dev-only secrets in `docker-compose.yml`, no HIPAA/SOC 2 claim, several intentionally simplified pieces like the rule-based triage severity map and the simulated voice/AI layer). PRD §23 is explicit that this distinction must be documented, not glossed over: **this deployment guide describes how to put the prototype somewhere publicly reachable for evaluation — it does not describe what would additionally be required to handle real PHI in production** (a real BAA with the hosting provider, encryption-at-rest configuration beyond whatever the host provides by default, a real incident-response process, a security review beyond this project's own testing, and replacing every placeholder named in `docs/known-limitations.md` with its real counterpart, at minimum).
