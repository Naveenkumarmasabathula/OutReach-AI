# Implementation Plan — Multi-Hospital Post-Discharge Outreach Platform

Status: Phases 0-11 complete; Phase 12's documentation is complete, hosted deployment and the demo video are not (see Phase 12's own row for why) (see the phase table below for exactly what each covers). See [requirements-summary.md](./requirements-summary.md) for the full must-have feature map and [multi-tenancy.md](./multi-tenancy.md) for the detailed tenant-isolation design this plan builds on.

## Tech Stack

Chosen to reuse proven patterns from `Documents/Zopkit/Project-Management-master` (a working multi-tenant Fastify/Drizzle/Postgres app) rather than starting from zero, per the decision to mould that project's approach onto this one. The reference project uses Fastify; this plan uses **Express 5** instead (swapped per review — see rationale below). This only changes the route-registration/guard layer in Phase 0 — the tenant-isolation design (schema, `HospitalScope`, RLS, RBAC) lives in the service layer and is framework-independent, so it transfers from the reference project regardless of web framework.

| Layer | Choice | Rationale |
|---|---|---|
| Language | TypeScript end-to-end | One type system across API, queue jobs, AI structured-output schemas (Zod), and frontend |
| Backend | Express 5 + TypeScript | Express 5 (not 4) specifically to get native async/await error handling — Express 4 does not catch rejected promises in route handlers by default. The reference project's guard/preHandler pattern (`{ preHandler: [authenticate, requireProjectAccess(...)] }`) is re-expressed as ordered middleware (`router.get('/:id', authenticate, requireHospitalAccess(...), handler)`) — same ordering discipline (hospital scope → visibility → module → capability), different syntax. Route-level schema validation has no Fastify-style built-in, so a small `validate(zodSchema)` middleware wraps each route instead |
| ORM / DB | Drizzle ORM + PostgreSQL | Matches the reference project's schema style (`pgTable`, CUID2 ids via `@paralleldrive/cuid2`) so its `schema/tenants.ts`-equivalent and query patterns can be adapted rather than redesigned — unaffected by the Express swap |
| Tenant isolation | App-layer explicit `hospital_id` filters (reference pattern) **+ Postgres RLS with `FORCE ROW LEVEL SECURITY`** (hardening — see [multi-tenancy.md](./multi-tenancy.md) §2) | PHI requires a DB-level backstop the reference project itself flags as a gap in its own design |
| Validation | Zod | Matches reference project; also used for AI structured-output schemas (triage results, escalation assessments) |
| Auth | Single JWT issuer (HS256, `jsonwebtoken`), simplified from the reference project's dual-IdP routing | One issuer is enough for this prototype; same `request.user` shape (`id`, `hospitalId`, `role`) |
| Queue/Scheduler | Redis + BullMQ, with a custom capacity-aware scheduling layer keyed by `hospital_id` | Neither BullMQ nor the reference project (which uses `node-cron` + SQS for simpler needs) has built-in per-tenant concurrency caps — this is the one component with no direct reference-project analog and needs original design (PRD §8, the top "critical" grading area) |
| AI | Google Gemini API (`@google/genai`); two independent assessment paths (LLM-based clinical triage + deterministic rule/protocol-matching triage) feeding a consensus/arbiter step | Satisfies "multiple independent assessments" (PRD §14) without multi-provider cost/complexity; the rule-based path is 100% reproducible for the safety evaluation (PRD §15). Swapped from Anthropic Claude to Gemini per product decision after Phase 3 — no Phase 5 code existed yet, so this only changed the package dependency and env var name, not any business logic (PRD §27's model-abstraction principle) |
| Frontend | React + TypeScript (Vite) | Reference project uses the same base (React 18 + Vite + TanStack); four role-based dashboards map onto TanStack Router/Query patterns already proven there |
| Voice | Deterministic conversation simulator first (must-have, PRD §12); real telephony (Twilio) as a stretch phase | Matches the PRD's explicit must-have/should-have split |
| Deploy | Docker Compose locally; Railway or Render hosted (Postgres + Redis + API + worker + web as separate services) | Supports multi-service + background workers + managed Postgres/Redis without new infra work |

## Multi-Tenancy

Full design in [multi-tenancy.md](./multi-tenancy.md). Summary: hospitals are the tenant root; every hospital-scoped table carries an indexed `hospital_id` with tenant-scoped (not global) uniqueness; `hospital_id` is sourced only from the authenticated principal and passed as an explicit `HospitalScope` object (mintable only by an access guard) into every service method; Postgres RLS is a forced second enforcement layer underneath the app-layer filters; background/queue jobs carry `hospital_id` explicitly on every payload; a dedicated isolation test suite (one file per domain, plus a completeness check across all tenant-scoped tables) is the CI safety net. This directly satisfies PRD §3's "tenant isolation must be enforced on the backend and data-access layer" and §23's security requirements, and is the top "critical" grading item alongside the queue.

| 4 — Protocols & Knowledge Retrieval | Hospital-scoped protocol/knowledge store, tenant-aware retrieval with source tracking — **complete**, see [protocols-knowledge-retrieval.md](./protocols-knowledge-retrieval.md); a pure/explainable keyword-tag ranking engine (mirroring the eligibility/priority engines), frontend included |
| 5 — AI Agent Layer | Voice Intake Agent (`VoiceProvider`/`SimulatedVoiceProvider`, matching the `EHRInterface`/`MockEHR` pattern — see [voice-provider.md](./voice-provider.md)), Clinical Triage Agent (two independent assessment paths — rule/protocol-matching + AI-model — both schema-validated), Escalation Decision System (consensus + conservative disagreement handling), Documentation Agent, the controlled-tool pipeline (authorization → validation → EHR interface → audit, see [ai-usage.md](./ai-usage.md)), persistent per-patient context, per-read PHI audit logging (`audit_log` table + `AuditedEHR` decorator) — **complete**. | 6 — Escalation & Human-in-the-Loop | Escalation lifecycle (acknowledge/assign/reassign/resolve, guarded transitions), a reviewer-facing detail view (patient + transcript + both independent triage assessments + consensus rationale), a real (simulated-delivery) notifications table — **complete**, see [escalation-management.md](./escalation-management.md), frontend included. Timeout-based auto-escalation to a backup reviewer is Phase 7 scope (needs the event/workflow bus) |
| 7 — Workflows & Events | Async event bus (BullMQ, reusing Phase 3's infrastructure) with durable-write-then-enqueue publishing and two-layer idempotent consumption, `hospital_id` explicit on every event payload — **complete**, see [workflows-events.md](./workflows-events.md). One concrete multi-step workflow built end-to-end (escalation notifies reviewers, then escalates to backup review on a hospital-configurable timeout); the other 14 catalog event types are published for audit/observability with no consumer wired yet |
| 8 — Dashboards & Analytics | Campaign Manager / Hospital Admin / Platform Admin dashboards, patient operational view, performance analytics (one `analyticsService.getHospitalAnalytics` computation feeding all of them) — **complete**, see [dashboards-analytics.md](./dashboards-analytics.md). This phase's own testing also found and fixed a critical, 100%-reproducible-under-load queue-concurrency race that had existed since Phase 3 — see [queue-design.md](./queue-design.md) |
| 9 — Safety Evaluation (**critical**) | Fixed 14-case eval dataset (routine/concerning/urgent/ambiguous/incomplete-information/conflicting-information/adversarial, 2 each), a repeatable runner (`npm run safety:evaluate`) over the real triage/consensus functions, TP/FP/TN/FN + false-negative-rate report, documented observed weaknesses — **complete**, see [safety-evaluation.md](./safety-evaluation.md) |
| 10 — Observability & Reliability | Real Healthy/Degraded/Unavailable health states (`GET /health`, dependency checks with timeouts), an AI-provider circuit breaker with a safety-conservative degraded fallback, correlation IDs for async job tracing (BullMQ job IDs), structured AI observability logging (model/latency/tokens/disagreement), and an audit-log extension covering human-driven "important operations" (campaign lifecycle, escalation reviews) — **complete**, see [observability-reliability.md](./observability-reliability.md). Prompt-injection hardening was already exercised in Phase 9's adversarial safety-eval cases, not repeated here |
| 11 — Testing | **Complete.** An audit against PRD §26's own testing checklist (not a blind coverage pass) found 5 genuine gaps in otherwise-thorough coverage built up over Phases 0-10: authentication *failure* paths (wrong password/nonexistent email/malformed/expired JWT — only "no token" was covered before), the central Zod-validation-error-to-400 handler, queue priority ordering at the `claimNextTasks` integration level (only the pure scoring function was tested), AI structured-output *rejection* (only valid output had ever been exercised), and `GeminiProvider`'s one-repair-then-throw retry logic (untestable without mocking, now covered via `jest.spyOn` on the real SDK client). All 5 filled — 145/145 tests passing across 23 suites (up from 116) |
| 12 — Deployment & Deliverables | Seed script, README, architecture diagram, queue design doc, safety report, AI usage doc, dev-AI-usage doc, known-limitations doc — **all complete**, see [architecture.md](./architecture.md). Hosted deploy and the demo video are the two PRD §33 deliverables not done: deployment is fully documented and ready to execute ([deployment.md](./deployment.md)) but requires a hosting-account decision only the project owner can make; the demo video needs actual screen recording, which isn't something this tool can produce — [demo-script.md](./demo-script.md) is the walkthrough to record it from |
| 13 — Stretch (should/nice-to-have) | Real Twilio telephony, streaming voice, richer analytics, EHR sync polish |

Phases 3, 5, 6, 9 map to the PRD's "Priority 1 — Critical" grading area (§34); 0–2, 4, 7, 8, 10–12 are "Priority 2 — Important." Phase 13 is optional and starts only after the must-haves are solid.

## Decisions (resolved)

1. ~~**Stack**~~ — **Resolved: Express 5** instead of Fastify (Drizzle/Postgres/BullMQ/React unchanged).
2. ~~**RLS as a second isolation layer**~~ — **Resolved: yes**, implemented from Phase 0.
3. ~~**Voice**~~ — **Resolved: simulator now** (`callSimulator.ts`, Phase 3; `VoiceProvider`/`SimulatedVoiceProvider` in Phase 5), real integration (Twilio or a hosted voice-AI platform) discussed as a documented later swap-in, not built now.
4. **Deployment target**: still open — Railway/Render, or a preferred host? Needed before Phase 12.
5. ~~**AI model tier**~~ — **Resolved**: mixed — a Gemini Pro-tier model (`gemini-3.1-pro-preview`) for the two safety-critical decisions (clinical triage, escalation consensus), a Gemini Flash-tier model (`gemini-3.5-flash`) for the rest (documentation). `GEMINI_API_KEY` has since been supplied and `GeminiProvider` live-verified; the flash tier works end-to-end, the pro tier is blocked by a zero-quota free-tier account (not a code issue) until billing is enabled — see [ai-usage.md](./ai-usage.md). `SimulatedAIProvider` remains what tests/required scripts run against, deliberately, for reproducibility.
6. ~~**Escalation notifications**~~ — **Resolved**: simulated/logged (structured, observable events) for now, not real email/SMS, matching the voice placeholder approach. Implemented in Phase 6 as a real `notifications` table (status always `simulated` today) rather than only a server log line, so "delivery must be observable" (PRD §19) means something queryable — see [escalation-management.md](./escalation-management.md).
