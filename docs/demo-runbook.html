Act 3 — Scale: watch the queue run

~2.5 minutes, mostly watching the terminal
Say "Outbound calling has hard limits — capacity, clinical deadlines, retry budgets. This isn't 'call everyone at once.' Watch the real scheduler."
Do — in your first spare terminal
  1. cd hospital/server
  2. Run the command below and let it play out on screen — don't narrate every line, let it breathe for a few seconds first.
$ npm run queue:simulate
Say, once it's mid-run "Every tick, capacity is strictly enforced — that number never gets exceeded, even with dozens of eligible patients waiting. Priority isn't insertion order, it's risk plus deadline pressure plus retry history. And in this single run you'll see every required outcome: a retry that exhausts into a manual follow-up, a callback that gets honored, a dropped call that recovers, a real escalation. It's deterministic — run it a hundred times, get the same guarantees every time."
Note: this command creates its own throwaway demo hospital each run — that's intentional and harmless, it never touches Riverside/Lakeside/Metro's data.

If they push back — quick answers

"Is the AI conversation actually live, or scripted?"
Both exist. The Voice Intake Agent is a deterministic simulator for the required demo (real telephony is explicitly a stretch goal, not required), but the triage/consensus logic you just watched decide the escalation is the exact same code path that runs in production — not a separate demo-only shortcut.
"What stops one hospital from seeing another's patients?"
Two independent layers: every query is scoped by hospital ID in application code, and Postgres Row-Level Security enforces the same boundary at the database layer as a backstop — so even a bug in the app code can't leak data across tenants.
"What happens if the AI provider goes down?"
A circuit breaker opens after repeated failures and the system falls back to a conservative default — escalate for human review — rather than silently guessing or failing calls outright.
"How do you know the queue won't overload the phone lines?"
Capacity is enforced centrally with row-level locking at claim time — proven under actual concurrent load in the test suite, not just assumed. You just watched it hold the line in the simulation.
"What's still missing / not production-ready?"
Real telephony (currently simulated by design — a documented stretch goal), and a handful of prototype-level tradeoffs disclosed candidly in the project's own known-limitations doc rather than hidden. Happy to walk through them.
