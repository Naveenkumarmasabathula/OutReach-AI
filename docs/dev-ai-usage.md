## Phase 0 + Phase 1 (foundations, hospital/patient data model)

**Tool**: Claude Code (Sonnet 5), agentic coding session.

**What was AI-driven**:

**Real bugs the AI introduced and then caught itself, via typecheck/test/manual verification rather than by inspection alone**:
- `declare const scopeBrand: unique symbol` was type-only and had no runtime value, but was used as a computed object property key at runtime in `mintHospitalScope` — caused a `ReferenceError` at seed time, only surfaced by actually running the seed script. Fixed by using a real `Symbol()` runtime value.
- Initially planned to enable `FORCE ROW LEVEL SECURITY` without accounting for the fact that Postgres superusers (including the docker-compose bootstrap Postgres user used for migrations) unconditionally bypass RLS regardless of `FORCE`. Caught before it shipped by checking `pg_roles`/`pg_class` after migrating — added a dedicated non-superuser `app_runtime` role for the app to connect as, verified via `\du` and `relforcerowsecurity` that the fix actually took effect.
- Several service methods (`createHospital`, `createPatient`, `createEncounter`, `createHospitalUser`, `createPlatformAdmin`) returned `T | undefined` from an unchecked array-destructure of an insert's `.returning()` result, only surfaced by `tsc --noEmit` under `noUncheckedIndexedAccess` at call sites (not in the functions themselves). Fixed with an explicit `assertDefined` helper rather than silencing with non-null assertions.
- A `drizzle-orm` version with a known high-severity SQL-injection advisory (identifier escaping) was initially installed; caught via `npm audit` immediately after install and upgraded before any schema/query code ran against a real database.

**Verification performed, not just assumed**: `tsc --noEmit` after every batch of changes; `npx drizzle-kit generate` output inspected for correct table/column/FK/index counts; RLS state verified directly via `psql` (`relrowsecurity`/`relforcerowsecurity` flags, policy definitions, role attributes) rather than trusting the migration "succeeded" message alone; end-to-end `curl` smoke tests of login, own-hospital access, platform-admin restrictions, and cross-hospital patient access (expecting and confirming 404, not 403, and confirming the excluded patient never appears in the other hospital's list); the Jest integration suite run against the real Postgres/Redis containers.

## Frontend (initial build)

**Tool**: Claude Code (Sonnet 5), same agentic session.

**What was AI-driven**: Given a design spec (an analysis of Apple's marketing-site design language) with an explicit instruction to use it for the frontend, first flagged and got user confirmation that the marketing-page structure (full-bleed hero tiles, alternating light/dark sections) shouldn't be transplanted onto a dense operations dashboard — then extracted the reusable token language (color, type, spacing, radius, elevation discipline) and applied it to a conventional dashboard chassis instead. Built the full component library, app shell, and all pages covering the backend's current API surface (auth, hospital admin, patient/encounter CRUD, staff management).

**Real bugs found and fixed during verification, not just written and assumed correct**:
- **Tailwind v4 spacing-token collision.** Custom theme tokens named `xs/sm/md/lg/xl` (matching the design doc's own naming) silently redefined Tailwind's reserved `max-w-*`/`min-w-*` container-width keywords, since both utility families read from the same `--spacing-*` theme namespace. Every card on the login page collapsed to near-zero width. Caught only by actually loading the page in a real browser and inspecting computed styles/bounding boxes — the production build succeeded and looked fine from the build log alone. Fixed by namespacing custom tokens (`ds-` prefix) and documented as a reusable lesson in `dashboard-design-system.md`.
- **React Router nested-`<Routes>` bug.** Rendering a second, independent `<Routes>` component as the `element` of a splat (`path="*"`) route — a pattern that looks like the documented "nested routers" approach — rendered an empty `<Outlet/>` with no console error at all in this React Router v7 setup. Caught by dumping the actual DOM (`<main>` was literally empty) after a route that should have shown content rendered blank. Fixed by flattening to one `<Routes>` tree with conditionally-included `<Route>` children instead of two nested `<Routes>` instances — the more standard pattern regardless.
- **A bulk shell rename that silently no-opped.** `grep -rlZ ... | xargs -0 perl -pi -e '...'` for a 46-occurrence find/replace across the frontend printed the matching filenames (making it look like it ran) but never actually edited most of them, due to a `-Z`/`xargs -0` interaction issue in this shell. Caught by re-grepping for the expected result after the "fix," not by trusting the command's exit code or output. Redone with a plain `for f in $(grep -rl ...)` loop, verified again afterward.

**Verification performed, not just assumed**: `tsc -b` and `vite build` after every change; a scripted Playwright pass (headless Chromium, installed for this purpose) against the **production build** (`vite preview`, not `vite dev` — dev-mode Tailwind scanning can lag, so preview was used specifically to rule out timing artifacts) driving real login flows for both a Hospital Admin and the Platform Admin, navigating every implemented page, and capturing screenshots + console-error checks at each step; screenshots were actually looked at (not just "no crash = pass") — this is how the spacing-collision layout bug was caught in the first place, since the build and typecheck both succeeded despite the broken layout.

## Phase 3: Outbound Queue & Scheduler (the PRD's top "critical" item)

**Tool**: Claude Code (Sonnet 5), same session. The user explicitly asked to be told about doubts/API-key needs *before* starting a large multi-phase push (Phases 3–11), and flagged that the voice/AI layer should be a swappable placeholder for now. Resolved two decisions with the user before starting (AskUserQuestion): the AI model tier for the app's own runtime decisions (Sonnet 5 for clinical-triage/escalation-consensus specifically, Haiku 4.5 for the rest — a cost/safety tradeoff genuinely the user's call, not mine to guess at) and escalation notifications (simulated/logged for now, matching the voice placeholder). Also caught and fixed a real, unrelated bug before starting Phase 3: the `encounters.riskLevel`/`campaigns.priority` schema comments claimed "1 = highest" for both fields, but the frontend's already-shipped severity badges and the eligibility criteria's actual semantics both treat *higher* `riskLevel` as more severe — the comments were backwards relative to real usage. Fixed the comments (not the behavior, which was already correct everywhere it mattered) before building a priority-scoring formula that would have baked in the wrong direction had the comment been trusted over the code.

**Design approach**: `priorityService.ts`'s `computeTaskPriority` is a pure, weighted-sum function (deadline pressure 0.4, clinical risk 0.3, campaign priority 0.2, starvation-prevention wait-boost 0.1) with a documented, tested justification for every weight and for the cubic (not linear) deadline-urgency curve — PRD explicitly grades on "explain how priority is calculated... why one patient is selected before another," and `docs/queue-design.md` is written to answer that question directly, not just describe the code. Concurrency safety is a two-layer design: a live per-hospital (and per-campaign) capacity count bounds how many *new* claims one call attempts, and each individual claim is a conditional `UPDATE ... WHERE status = <expected>` — Postgres's row-level locking makes this atomic without an application-level lock. BullMQ (`worker.ts`) is the distribution layer on top of this, deliberately independent from it: by the time a task reaches a BullMQ job, capacity was already reserved in Postgres, so BullMQ's own worker concurrency setting never needs to coordinate with tenant capacity. The call-outcome simulator (`callSimulator.ts`) is hash-based, not `Math.random()`-based, specifically so Phase 9's safety evaluation can reproduce a scenario after a prompt/model change — a design constraint from a phase that doesn't exist yet, applied now because retrofitting determinism into a simulator later would be far more disruptive than building it in from the start.

**Real bugs found via testing, not written and assumed correct**:
1. **The core concurrency test failed to compile against the intended design** until `claimNextTasks` was written as a conditional compare-and-swap `UPDATE` rather than a read-then-write — caught immediately by `test/queue/queue.test.ts`'s dedicated concurrency test (6 concurrent `claimNextTasks` calls against a hospital with capacity 3 and 10 pending tasks), which asserts both that total claimed never exceeds capacity *and* that no task is claimed twice. The second assertion is the one that actually distinguishes a correct implementation from one that merely looks correct in a single-threaded test.
2. **`releaseStaleLocks`'s first implementation silently did nothing, always**, because it queried `outreach_tasks` (RLS forced) through the app's unscoped DB connection — that connection never sets `app.current_hospital_id`, so the RLS policy compares against `NULL` and matches zero rows regardless of real data. This is exactly the class of mistake `docs/multi-tenancy.md` itself names as the top data-safety review item, and it happened anyway, in code written with that document already in context. Caught by the stale-lock recovery test asserting `releasedCount >= 1` and getting 0. Fixed by enumerating hospitals from the unscoped, non-RLS `hospitals` table and running a properly `withHospitalScope`-wrapped query per hospital — never a global query against a forced-RLS table. The *test's own* helper code had the identical bug (backdating a task's `lockedAt` via the unscoped connection) and needed the same fix.
3. **A real integration gap, not a bug in either service alone**: nothing called `queueService.enqueueEligiblePatients` when a campaign started or resumed — `campaignService.startCampaign` only flipped the status. Caught by a live `curl`+worker smoke test (a "started" campaign showed zero queue activity) before it ever reached a unit test. Fixed at the route layer, not inside either service, specifically to avoid a circular module dependency (`queueService` already imports `campaignService` for calling-hours lookups; the reverse import would cycle) — routes are the right place to coordinate two services that structurally can't depend on each other.
4. **The required simulation script's showcase scenarios contaminated each other**: all 5 "showcase" patients were enqueued up front, so claiming for the first one could sweep up the others as spare capacity and resolve them through the real (random-seeming) simulator before their own scripted outcome ever ran — the exact bug the showcase design was supposed to prevent, reintroduced by batching the setup. Fixed by creating and enqueuing each showcase patient immediately before its own scripted sequence, one at a time, so at most one showcase task is ever pending at once.
5. **The showcase retry-exhaustion sequence failed on its second forced outcome** because the task's `scheduledFor` was a real 30-minute-future backoff time from the first attempt — retrying the claim loop in a tight cycle can't fix a task that genuinely isn't due yet. Fixed by having `claimAndForceOutcome` fast-forward the target patient's task to "due now" before each claim, clearly commented as a demo-only clock advance that doesn't touch the backoff algorithm itself (which already ran for real on the previous step).

**Verification performed**: `tsc --noEmit` after every file; the 9-assertion `priorityService` unit suite (including a direct test of the PRD's own "near-expiry beats high-priority-but-fresh" example, and a test that the wait-boost alone can never outrank real urgency); the 10-assertion `queueService` integration suite against real Postgres (capacity enforcement, the concurrency guarantee, retry/callback/escalation/manual-follow-up transitions each verified by driving `recordAttemptOutcome` directly rather than fighting the simulator's hash, stale-lock recovery, tenant isolation) — 50 tests total across all suites, all passing; a live end-to-end smoke test starting the actual `worker.ts` process against real BullMQ+Redis and watching it claim and process 21 real queued tasks within one scheduler tick, then confirming the resulting escalation records actually exist in Postgres; the required `npm run queue:simulate` script run to completion multiple times while debugging, each run's output read and checked against what it claimed to demonstrate, not assumed correct because it didn't crash; all test/demo data cleaned from the dev database between iterations, with the final simulation run's data deliberately left in place as the actual deliverable.

## Phase 8: Dashboards & Analytics

**Tool**: Claude Code (Sonnet 5), same session, continuing directly from Phase 7 per "complete the rest of the implementation... complete upto 11."

**What was AI-driven**: Designed `analyticsService.getHospitalAnalytics` as one comprehensive aggregation rather than a metric-per-endpoint API, since every metric PRD §20 lists is a plain grouped-count query over already-tenant-scoped tables and a dashboard needs all of them together. Deliberately computed two distinct timing metrics (historical "time-to-contact" vs. live "queue wait") rather than collapsing them, since PRD §20 names both and they answer genuinely different operational questions. Extended Phase 1's `getPatientTimeline` for the patient operational view rather than adding a new endpoint, continuing the established "one enriched read, extended in place" pattern.

**A critical, previously-undetected bug found via this phase's own testing, unrelated to analytics itself**: running the new analytics suite as part of the *whole* backend test suite (not in isolation) surfaced an intermittent failure in the queue's core concurrency-safety test — the single most important guarantee in the entire platform. Investigated rather than dismissed as flakiness: wrote a standalone stress script forcing 20 concurrent `claimNextTasks` calls against a capacity-3 hospital, which reproduced a massive over-claim (30 tasks claimed against a capacity of 3) **100% of the time**, confirming a genuine, always-reproducible-under-load race in code that had shipped in Phase 3 and passed every prior test run — the bug existed for five phases before being caught, specifically because the existing test's concurrency level (6 callers) wasn't high enough to reliably trigger it in a fast, unloaded single-file run, only under real parallel load. Root cause: the live capacity count was an unlocked `SELECT` under READ COMMITTED, so N concurrent callers for the same hospital could each read stale pre-commit state and each independently claim up to the full capacity via otherwise-correct per-row atomic updates — no row was ever double-claimed, but the *aggregate* limit was never actually enforced across concurrent transactions. Fixed with a Postgres advisory transaction lock (`pg_advisory_xact_lock(hashtext(hospitalId))`) as the first statement in `claimNextTasks`'s transaction, serializing claims per-hospital without a schema change or touching the capacity math itself. Verified the fix, not just the absence of the original symptom: re-ran the same 20-concurrent-caller stress script 15 times with the fix in place — exactly at capacity, every time — then reverted the fix temporarily to re-confirm the stress script still reproduces the original failure (it did, 15/15), before restoring the real fix. This before/after verification against the same reproduction script is the strongest evidence available that the fix addresses the actual mechanism, not just a symptom. Also strengthened the permanent regression test from 6 to 20 concurrent callers, chosen empirically (not arbitrarily) to match what was needed to make the regression this guards against reliably reproducible rather than "usually" reproducible.

**A real, if narrower, performance bug found the same way**: `getPlatformAggregateAnalytics`'s first draft used `Promise.all` across all hospitals, which stalled badly once tested against the dev database's 200+ accumulated test hospitals (a side effect of this being a long, single continuous session with a shared, never-reset dev database) — each hospital's analytics call opens several of its own pool connections, and firing all of them concurrently fanned out to many times the Postgres pool's size. Fixed by processing hospitals sequentially; confirmed the platform aggregate call completes in about a second against the same 200+-hospital dataset that previously stalled it past a reasonable timeout.

**Verification performed**: `tsc --noEmit` on `server`, `npm run build --workspace web`; the new 5-assertion `analytics.test.ts` suite run against real Postgres — 97/97 tests passing across all suites (up from 92), the full suite run three consecutive times specifically to confirm the concurrency fix holds under the same real parallel load that originally exposed the bug, not just once; a live smoke test logging in as the real seeded Hospital Admin, Campaign Manager, and Platform Admin users against the real running app (backend started on an alternate port for this session specifically to avoid an unrelated project already using port 4000 on this machine, with the port change reverted immediately after testing) and driving all three dashboards via Playwright, confirming genuinely role-differentiated content and reading real aggregated numbers rendered on the page, zero browser console errors.
