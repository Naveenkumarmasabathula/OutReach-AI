# Observability & Reliability (Phase 10, PRD §21-22)

## What this covers

Real health-state reporting (Healthy/Degraded/Unavailable), a circuit breaker + safe degradation for AI provider outages, correlation-ID tracing for async workflows, AI observability logging (model, latency, token usage, disagreement), and closing a gap Phase 5 explicitly deferred here: audit records for human-driven "important operations," not just AI PHI reads.

## Design

**Health states map to real dependency checks, not a hardcoded string.** `lib/systemHealth.ts`'s `getSystemHealth()` actually queries Postgres (`SELECT 1`) and pings Redis, each with its own timeout so a hung dependency can't hang the health check itself. Database and Redis are treated as hard dependencies (either failing means `unavailable`) since the platform genuinely cannot function without either; a degraded AI provider (its circuit breaker open) is only `degraded`, since outreach calls that don't need triage keep working and connected calls fall back to a conservative single-assessment mode rather than failing outright. `GET /health` is deliberately unauthenticated and cheap — it doubles as an external liveness/readiness probe, not just an internal dashboard signal — and maps `unavailable` to a real HTTP 503 so a load balancer or uptime monitor can act on the status code alone.

**The circuit breaker (`ai/circuitBreaker.ts`) targets AI provider outages specifically**, the concrete PRD-named failure mode this project's other dependencies already have their own recovery story for (Postgres/Redis failures surface as thrown errors the central error handler turns into a 500; BullMQ's own `attempts`/backoff already retries transient job failures). After 3 consecutive failures it opens for a cooldown, short-circuiting further calls immediately rather than piling up slow, doomed requests against a known-failing provider; a half-open trial call after the cooldown closes it again on success or re-opens it on failure.

**The fallback when the circuit is open is deliberately conservative, not silent.** `degradedFallbackAssessment` doesn't guess a plausible-looking classification — it returns `"uncertain"` with zero confidence and an explicit `escalationRecommended: true`, and its `reasoning` field says outright that a real second opinion couldn't be obtained. Paired with the rule-based path's own (still-real) assessment in `decideEscalation`'s worst-of logic, this guarantees the consensus is at least `"uncertain"` — flagged for human review — whenever the AI path is degraded, never a falsely confident `"routine"`. This is a direct application of PRD §14's own premise (never trust a single assessment path) to the *failure* case, not just the happy path.

**AI observability is one structured log line per triage run** (`ai/pipeline.ts`), not scattered across every function — provider name, latency, protocols retrieved, disagreement, consensus classification, and the actual escalate decision, all without a single patient-identifying field (PRD §21: "sensitive healthcare information must not be unnecessarily written into logs" — everything logged here is either a count, an id, or a classification, and every one of those same values is already durably persisted on the escalation/attempt rows this same run produces, so nothing new is exposed by logging it). `GeminiProvider` separately logs token usage (`promptTokenCount`/`totalTokenCount`) per call when available — estimated dollar cost is deliberately not computed, since that needs current per-model pricing as an input that isn't safe to hardcode and silently let go stale.

**Correlation IDs reuse BullMQ's own job IDs rather than inventing a parallel ID scheme.** Every async job handler (`worker.ts`) now logs `job.id` at the start of processing, not only on failure (which was already logged) — for the outreach-call queue, `job.id` is the task ID (already the case, an existing dedup guard doing double duty); for the events and escalation-timeout queues, the event/escalation ID. HTTP requests already had `pinoHttp`'s own correlation ID (`x-correlation-id` header or a generated UUID) from Phase 0 — this phase's job was specifically closing the gap on the *asynchronous* side, which had no equivalent before.

**Audit logging for human-driven "important operations" reuses the exact same `audit_log` table and `recordAudit` function Phase 5 built for AI-agent PHI reads** — this was an explicitly promised Phase 10 follow-up (`docs/known-limitations.md`'s Phase 5 entry said so directly), not new infrastructure. A thin `auditUserAction` route helper avoids repeating the actor/scope boilerplate at each of the ~13 new call sites: every campaign lifecycle action (create, ready, start, pause, resume, cancel, complete, reprioritize) and every escalation reviewer action (acknowledge, assign, start review, request information, resume review, resolve, close) now writes one. The AI pipeline's own escalation-creating consensus decisions get a matching entry too (`escalation.ai_consensus_decision`, actor `ai_agent`) — PRD §21 names "AI escalation assessments, consensus decisions" as their own audit category, distinct from "staff reviews." A minimal read path (`GET /api/v1/audit-log`, `GET /api/v1/platform/hospitals/:id/audit-log`) was added alongside this — the `audit.read` permission has existed since Phase 0's original RBAC design but had nothing to authorize until now, and an audit trail nobody can inspect isn't meaningfully auditable.

**Queue-specific health gained a `stuckTasksCount` field** (`queueService.getQueueHealth`) — tasks still marked `'calling'` past the same staleness threshold `worker.ts`'s stale-lock sweep uses to actually recover them (now a single shared exported constant, `STALE_LOCK_THRESHOLD_MINUTES`, rather than duplicated in two files). A nonzero count surfaces on the campaign detail page's Queue card as a critical badge — "stuck (crashed worker?)" — giving a human-visible signal for exactly the PRD §21 field this was missing.

## What was deliberately not built now

- **Cost estimation for AI usage** — see "AI observability" above; token counts are logged honestly, a dollar estimate is not fabricated.
- **A dedicated frontend page for browsing the audit log or event log.** The read API exists and is tested; a UI for it is reasonable future work if evaluators specifically want to browse it, but wasn't judged essential given the scope remaining in Phase 11.
- **Extending `AuditedEHR`-style per-read audit wrapping to every pre-existing human-facing PHI route** (patient detail pages, encounter lookups) — still out of scope, same reasoning as Phase 5's original deferral: this is a larger, separate refactor touching many existing routes, distinct from adding audit records for the specific "important operations" PRD §21 names by name (which this phase did complete).
- ~~A circuit breaker for the Voice Provider or EHR interface~~ — **built in the reliability-audit follow-up below.** `MockEHR` gained a real (if artificial) way to fail — `mockEhrConfig.simulatedFailureRate` — which made this both meaningful and testable; see "Reliability audit follow-ups" below.

## Reliability audit follow-ups (this pass)

A later audit against this same PRD §21-22 scope found several concrete gaps in what Phase 10 shipped. Each is its own fix, numbered to match the audit:

**Fix #1 — EHR and voice-provider circuit breakers.** `ehr/circuitBreakerEhr.ts` and `voice/circuitBreakerVoiceProvider.ts` add `CircuitBreakerEHR`/`CircuitBreakerVoiceProvider`, both decorators over their respective interfaces (same shape as `AuditedEHR`), both built on the exact same `CircuitBreaker` class from `ai/circuitBreaker.ts` — not a second implementation. Wired in at the single swap point each module already had (`ehr/index.ts`: `new CircuitBreakerEHR(new MockEHR())`; `voice/index.ts`: `new CircuitBreakerVoiceProvider(new SimulatedVoiceProvider())`), so every existing caller (including `AuditedEHR`, which wraps the already-wrapped `ehr` singleton in `ai/pipeline.ts`) gets the protection for free. **What "degraded" means for EHR, unlike AI: there is no safe conservative fallback.** The AI breaker substitutes a conservative `"uncertain"` assessment when open; the EHR/voice breakers substitute nothing — a communication log, observation, follow-up task, or escalation record that silently didn't get written would be a data-loss bug, not a graceful degradation, and a fabricated transcript would be actively harmful once it fed into triage. So when either circuit is open, every call — read or write — throws an explicit `ServiceUnavailableError` (503, new in `lib/errors.ts`) immediately, never hangs or gets silently swallowed. A `NotFoundError` (patient/encounter genuinely out of scope) is deliberately *not* counted as a circuit failure — that's the EHR correctly answering "no such record," not an outage. Tested against fake `EHRInterface`/`VoiceProvider` implementations (`test/unit/ehrCircuitBreaker.test.ts`, `test/unit/voiceCircuitBreaker.test.ts`) so the breaker logic itself is exercised deterministically, independent of whether the real Postgres-backed `MockEHR` happens to be failing.

**Fix #2 — idempotency for notifications and EHR writes.** `notificationService.sendNotification` and `MockEHR`'s four insert-style writes (`writeCommunication`, `writeObservation`, `createFollowUpTask`, `createEscalationRecord`) now accept an optional `idempotencyKey`. When supplied, each does a check-then-insert against a new `(hospital_id, idempotency_key)` unique index (nullable column, so every existing caller that omits the key is completely unaffected — Postgres treats every `NULL` as distinct in a unique index) plus `onConflictDoNothing` as a second, DB-enforced guard against a genuine race between two concurrent retries. `updateEncounterMock` was deliberately *not* given this treatment — a `SET` of specific fields is already idempotent by construction, re-running it twice yields the same row state, unlike an insert. Wired into two real HTTP-triggered-and-retriable call sites (`escalationService.acknowledgeEscalation`/`assignEscalation`, `events/escalationTimeout.ts`'s admin notification loop, which genuinely can double-fire on a redelivered job since nothing else guards it). **Known gap, and why:** `queueService.ts`, `ai/pipeline.ts`, and `events/handlers.ts` — the primary outreach-call write path — were owned by other engineers mid-edit during this pass and explicitly off-limits to touch; they still call these same functions without an `idempotencyKey`, so that specific path doesn't yet get the new protection. The mechanism is fully built and tested (`test/ehr/ehrIdempotency.test.ts`, `test/notifications/notificationIdempotency.test.ts`); threading a key through from those three files (a natural key like `<outreachTaskId>:<operation>` is right there in `queueService.ts`'s existing call sites) is a follow-up for whoever owns them next.

**Fix #3 — platform-wide queue health on `GET /health`.** `lib/systemHealth.ts`'s new `getAggregateQueueHealth()` adds a `queue` field to `SystemHealthReport` with all 7 PRD §21 fields (`activeCalls`, `capacity`, `pendingWork`, `oldestPendingScheduledFor`, `tasksNearCutoff`, `failedTasks`, `stuckWorkers`), aggregated across every `active`-status hospital. It reuses `queueService.getQueueHealth(scope)` verbatim, once per hospital (the same enumerate-then-scope pattern `queueService.releaseStaleLocks` already uses for the same RLS-forced-table reason), and sums the results client-side rather than reimplementing the per-status/cutoff/stuck-worker SQL a second time. Only aggregate counts and one timestamp — nothing patient- or hospital-identifying — since `/health` is still deliberately unauthenticated. Its own timeout (same `CHECK_TIMEOUT_MS` pattern as the database/redis checks) means a slow rollup degrades to `queue: null` rather than hanging the whole endpoint.

**Fix #4 — correlation IDs in BullMQ job data.** Every job-data type in `queue/queues.ts` (`ProcessCallJobData`, `ProcessEventJobData`, `EscalationTimeoutJobData`) now carries an optional `correlationId`, logged on every one of `worker.ts`'s "Processing X job" log lines. `events/publish.ts`'s `publishEvent` takes an optional 4th `correlationId` argument and generates a fresh `randomUUID()` when none is given — which is what happens for every pre-existing caller (`queueService.ts`, `campaignService.ts`, `events/handlers.ts`, all off-limits this pass) and for `worker.ts`'s own scheduler-tick-originated `outreachQueue` jobs, matching this fix's own stated allowance: a job with no real originating HTTP request just gets a fresh id at enqueue time. Where a real originating request *does* exist and the owning file was editable, it's threaded through for real: `routes/escalations.ts`'s acknowledge/resolve handlers pass `req.id` (pino-http's own per-request id) into `escalationService.acknowledgeEscalation`/`resolveEscalation`, which pass it to `publishEvent`, which puts it on the `escalation.acknowledged`/`escalation.resolved` event's job data — a genuine HTTP-request → async-worker-log trace, not just a freshly minted id at the queue boundary. Tested in `test/unit/correlationId.test.ts` by spying on `eventsQueue.add`.

**Fix #5 — PHI log redaction is now a real mechanism.** `lib/logRedaction.ts` exports `PHI_LOG_REDACT_PATHS`/`PHI_LOG_REDACT_CENSOR`, used by `app.ts`'s `pinoHttp({ redact: {...} })` config (previously only `req.headers.authorization`). The field list was checked against actual request body shapes, not guessed: `createPatientSchema` (`mrn`/`firstName`/`lastName`/`dateOfBirth`/`phone`/`email`), the escalation review routes' free-text `notes`/`resolution` fields, and auth/user-creation's `password`. `transcript`/`conditions` are redacted too (wildcarded across nesting depth, `*.transcript`/`*.conditions`) even though no request body accepts either today — forward defense per the original audit's own suggestion, a no-op now, real protection the moment either ever flows through a logged request body. **Honest scope, not oversold:** this only covers whatever ends up inside a *logged* `req`/body-shaped object on the `pinoHttp`-configured logger specifically. The separate base `logger` instance (`lib/logger.ts`, used directly by services) has no redact config at all — its own comment now says so explicitly, and the existing discipline ("log identifiers and outcomes, not PHI content") still has to hold there. This is a blunt backstop for one path, not a blanket PHI-log-safety guarantee.

**Fix #6 — prompt versioning.** `ai/geminiProvider.ts` adds `TRIAGE_PROMPT_VERSION`/`DOCUMENTATION_PROMPT_VERSION` constants (manually bumped per prompt area, not a full versioning system) and includes whichever applies as `promptVersion` on the same "Gemini call completed" log line that already carries model/latency/token counts — so a prompt-wording change becomes traceable against those same numbers over time.

**Fix #7 — seed data had zero outreach history.** `db/seed.ts` now generates a deterministic outreach history (`outreach_tasks` + `outreach_attempts`, cycling through 9 fixed scenarios) for a subset of each hospital's patients, covering every PRD §5-named outcome (`completed`, `no_answer`, `busy`, `dropped`, `callback_requested`, `escalated`) plus tasks left in `manual_follow_up`/`failed`/still-`pending` states, and a few real `escalations` rows — all keyed off each patient's own stable `mrn` through the same FNV-1a hash-to-unit-interval technique `services/callSimulator.ts` already uses for reproducible "randomness," so re-seeding produces the same data. `medications`/`procedures` (previously dead schema — no seed data, no EHR read path) get a handful of deterministic rows per patient, and `MockEHR`/`EHRInterface` gained `getMedications`/`getProcedures`, mirroring `getConditions`/`getObservations` exactly. Verified by actually running `npm run db:seed` against the dev database (not just reading the code): 27 patients per hospital get outreach history (3 of each of the 9 scenarios), 3 real escalations per hospital, and every patient gets 1-3 medications + 0-2 procedures.

## What's still not done after this pass

- **Fix #2's idempotency isn't threaded through the primary outreach-call write path** (`queueService.ts`/`ai/pipeline.ts`/`events/handlers.ts`) — see Fix #2 above for exactly why and what the follow-up looks like.
- **Correlation IDs don't reach every worker log line's downstream service calls** — `worker.ts` logs `correlationId` at the top of each job, but deeper calls it makes (e.g. `checkEscalationTimeout`'s own `logger.warn` for a missing escalation) don't thread it further. The top-level job log is enough to tie a job's *start* to its trigger; tracing *within* a job's own downstream log lines is a further refinement, not done here.
- **The idempotency-key schema migration was applied directly to the dev database rather than through a clean, committed drizzle-kit migration file** — the shared `server/drizzle/` migration folder and its `meta/_journal.json` were being actively regenerated by concurrent work during this pass (files this session generated were observed being overwritten/removed moments later by another process), making a normal `drizzle-kit generate` + commit unsafe to attempt reliably. The five `idempotency_key` columns and their unique indexes (`communications`, `tasks`, `escalations`, `notifications`, `observations`) exist on the dev database today and the corresponding Drizzle schema files (`db/schema/*.ts`) already declare them — but whoever next runs a clean `drizzle-kit generate` should expect (and can safely accept) a migration proposing exactly these five additions, since they match what schema-as-code already says.
