# Dashboards & Analytics (Phase 8, PRD §20)

## What this covers

Role-differentiated operational dashboards (Campaign Manager, Hospital Admin, Platform Admin) and the analytics aggregation they're built on, plus an extended patient operational view (outreach status, call history/outcomes, escalations) on top of Phase 1's patient timeline.

## Design

**One analytics function, not one per dashboard.** `analyticsService.getHospitalAnalytics(scope)` computes everything PRD §20 lists in one call — campaign counts, outreach status/outcome breakdowns, average attempts, time-to-contact, queue wait, capacity utilization, escalation counts, manual follow-ups, eligible-patient counts, protocol counts, staff counts — because a dashboard needs all of them together, and every one of them is a plain aggregation over already-tenant-scoped tables, not something that benefits from being independently callable or cached separately.

**Two closely related but distinct timing metrics**, both explicitly asked for by PRD §20: "time-to-contact" is historical (how long after a task was *created* did its first real attempt actually start, averaged over tasks that have an attempt), while "queue wait" is live (how overdue, right now, are tasks still sitting in a claimable state past their own `scheduledFor`). Conflating them would have hidden the difference between "how well did we do historically" and "how backed up are we right now."

**One dashboard component, not three separate pages, for Campaign Manager and Hospital Admin.** Both roles read the exact same `/analytics/hospital` response and share almost all of their layout — the one genuine difference PRD §20 asks for (staff activity visibility) is Hospital-Admin-only and is a small conditional section, not a structurally different page. `CLINICAL_REVIEWER` has no `analytics.read` grant (unchanged from Phase 0's original RBAC design), so `OverviewPage`'s analytics query is disabled for that role via the same `enabled` pattern established back when `useMyStaff` had the identical issue.

**The Platform Admin dashboard is safe by construction, not by permission check alone.** `getPlatformAggregateAnalytics` builds its response entirely out of `getHospitalAnalytics`'s own return shape, summed and listed per hospital — there is no patient name, MRN, or any individually-identifying field anywhere in that data structure to accidentally leak, so PRD §20's "aggregate analytics must never bypass patient-level access controls" holds even if the permission check were somehow bypassed. Verified directly, not just argued: a test JSON-stringifies the full aggregate response and asserts a real patient's first name, last name, and MRN never appear in it.

**The patient operational view (PRD §20: "discharge info, outreach status, call history, outcomes, escalations, observations, documentation, follow-up actions") extends Phase 1's `getPatientTimeline`** rather than adding a new endpoint — that function was already the "give me everything about this patient" call every prior phase has extended in place (Phase 1's own conditions/medications/procedures/etc., unchanged here), and adding `outreachTasks`, `outreachAttempts`, and `escalations` to it keeps that pattern rather than fragmenting patient data access across multiple endpoints.

## A critical bug found while building this phase, unrelated to analytics itself

Running the full analytics test suite as part of the whole backend suite (not in isolation) surfaced an intermittent failure in `test/queue/queue.test.ts`'s core concurrency-safety test — the single most important guarantee in the entire platform (PRD §8/§10: "two workers must never... exceed the configured concurrency limit"). Investigation found a genuine, 100%-reproducible-under-load race condition in `claimNextTasks` that had existed since Phase 3 and gone undetected: the live capacity count was an unlocked read, and enough concurrent callers for the same hospital could each read stale pre-commit state and collectively claim well past real capacity. Fixed with a Postgres advisory transaction lock. Full details, including the exact stress-test numbers before and after the fix, are in `docs/queue-design.md`'s "Concurrency control" section and `docs/known-limitations.md`'s Phase 3 entry — not repeated here since this doc is about dashboards, but flagged here because it's exactly the kind of thing "run the whole suite, not just the file you think is relevant" is for, and it was this phase's own test run that surfaced it.

## What was verified

- `tsc --noEmit` on both `server` and `web`; `npm run build --workspace web`.
- New test suite (`server/test/analytics/analytics.test.ts`, 5 assertions): correct aggregation of campaigns/outcomes/escalations/eligible-patient-counts for a seeded scenario, tenant isolation between two hospitals, the platform aggregate's real summation across real hospitals *and* its structural non-leakage of patient-identifying fields, and HTTP RBAC for both the hospital-scoped and platform-scoped analytics endpoints. Full suite: 97/97 passing (was 92 before this phase), run three consecutive times to confirm the concurrency fix holds under repeated real parallel load, not just once.
- A real performance issue found and fixed, not just a test inconvenience: `getPlatformAggregateAnalytics`'s first draft ran all hospitals through `Promise.all`, which is fine for a handful of hospitals but fanned out to many times the Postgres connection pool's size once the dev database had accumulated 200+ hospitals across this long session's repeated test runs — the platform dashboard call effectively stalled. Fixed by processing hospitals sequentially instead; confirmed with the same 200+-hospital dataset that the aggregate call now completes in about a second.
- Live smoke test: logged in as the real seeded Hospital Admin, Campaign Manager, and Platform Admin users against the real running app and drove all three dashboards via Playwright — confirmed genuinely different content per role (staff-by-role only for Hospital Admin, the Platform Admin's per-hospital table showing real aggregated numbers across the dev database's actual hospitals), zero browser console errors on any of the three.

## What was deliberately not built now

- **Pagination on the Platform Admin's per-hospital table.** Fine for the current data volumes; a real concern only at a scale this prototype doesn't need to plan for yet.
- **A dedicated analytics page separate from the Overview dashboard** — the data is the same either way; a separate `/analytics` route would only be useful once there's meaningfully more content than fits in an overview (e.g., historical trend charts), which is out of scope for this phase.

## Backend follow-up: AI usage / errors / system performance / EHR write activity (post-audit fix)

A later audit found this phase's original build had left three PRD §20/§22 gaps unaddressed on the **backend**. This section documents the backend-only fix; the corresponding dashboard UI work is a separate, subsequent change (the person doing it is doing a full UI redesign and will wire these fields into new components — nothing under `web/src/` changed as part of this fix).

**1. Platform Admin "AI usage, errors, and system performance" (PRD §22).** The original phase left this out entirely (see the old "deliberately not built" bullet this section replaces) because nothing durably persisted AI call outcomes — `ai/pipeline.ts` only ever `logger.info`'d them. Fixed with:

- A new `ai_call_log` table (`server/src/db/schema/aiCallLog.ts`, migrations `0017`/`0018`) — one row per AI agent call: `hospitalId`, `agentType`, `provider`, `model`, `latencyMs`, `success`, `createdAt`. Deliberately minimal, and free of transcript/PHI content (same posture as the existing pipeline log line).
- A write-side helper, `aiCallLogService.recordAiCall(scope, input)` — **not called from anywhere yet**. `ai/pipeline.ts` is owned by another engineer and wasn't touched by this fix; wiring a call to `recordAiCall` in there (e.g. right after its existing "AI triage pipeline run completed" log line) is the one remaining step, tracked here rather than done silently. Until that lands, `ai_call_log` stays genuinely empty and every AI-usage number below is honestly zero — not a fabricated placeholder, a real aggregation over a real (currently empty) table.
- A read-side aggregation, `analyticsService.getAiUsageStats(scope: HospitalScope)`, returning `{ totalCalls, byAgentType, successCount, failureCount, successRate, averageLatencyMs }`. `getHospitalAnalytics`'s return gained an `aiUsage` field with this same shape (computed via a shared internal helper against the transaction it already has open, to avoid opening a second DB connection per hospital — see below). `getPlatformAggregateAnalytics`'s return gained a top-level `aiUsage` (summed across hospitals, with `averageLatencyMs` correctly volume-weighted) and each `perHospital` entry gained its own `aiUsage`.
- "Errors" and "system performance" were already fully computable from existing data, so no new table was needed for those: `getPlatformAggregateAnalytics`'s new `errors: { failedTaskCount, technicalFailureCount }` sums each hospital's existing `outreach.byStatus.failed` and `outreach.byOutcome.technical_failure` (queue task failures and AI-pipeline/technical attempt failures, respectively — both already tracked by `queueService.ts`, untouched by this fix). The new `systemPerformance: { activeCalls, outboundCapacity, queueUtilization }` deliberately reuses the same capacity/utilization numbers already computed in `totals`, rather than a second, separately-computed signal that could drift from it.

**2. Hospital Admin "EHR synchronization status" (PRD §22).** The EHR here is `MockEHR` — there is no real external system to "sync" with, so a literal sync-status field would be fabricated. Instead, `getHospitalAnalytics`'s return gained an honest **EHR write activity** proxy: `ehrWriteActivity: { windowHours: 24, communications, observations, manualFollowUpTasks, escalationRecords, total }` — a count of rows actually written through the EHR interface (`communications`, `observations`, `tasks` of type `manual_follow_up`, `escalations`) in the last 24h, per hospital. Deliberately not called "sync status" anywhere in the code or here, since it isn't one.

  EHR-write **failure** tracking was considered and dropped: `server/src/ehr/auditedEhr.ts` explicitly only audits *reads* ("Writes are not wrapped — ... every write already produces its own durable row that is itself the record"), so `audit_log` has no EHR-write-failure signal to aggregate. `MockEHR`'s writes are plain DB inserts inside a transaction — they either succeed and commit, or throw and the whole call fails (no partial/"logged failure" state exists to count). Reporting a fabricated failure rate would have been worse than omitting it, so "activity," not "activity + failures," is what's reported.

**3. `getQueueHealth`'s `oldestPendingScheduledFor` (previously computed but unrendered).** Confirmed still reachable and unchanged: `GET /api/v1/campaigns/:campaignId/queue-health` (`server/src/routes/campaigns.ts`) returns `queueService.getQueueHealth`'s result verbatim, which includes `oldestPendingScheduledFor` alongside `byStatus`, `tasksNearCutoff`, and `stuckTasksCount`. No backend change was needed — the data was already exposed on an existing endpoint; the UI simply never bound to it. `queueService.ts` was not touched by this fix.

**New fields at a glance** (added to existing endpoints, nothing new to wire up on the routing side):

- `GET /api/v1/analytics/hospital` (`getHospitalAnalytics`): `+ aiUsage`, `+ ehrWriteActivity`.
- `GET /api/v1/platform/analytics` (`getPlatformAggregateAnalytics`): `+ aiUsage`, `+ errors`, `+ systemPerformance`; each `perHospital` entry gains `+ aiUsage`, `+ errors`.
- `GET /api/v1/campaigns/:campaignId/queue-health` (unchanged): already includes `oldestPendingScheduledFor`.

Tested in `server/test/analytics/analytics.test.ts`: real aggregation of `ai_call_log` rows written directly via `aiCallLogService.recordAiCall` (simulating what `ai/pipeline.ts` will do once wired) and read back identically through both `getAiUsageStats` and `getHospitalAnalytics`; the all-zero/empty state before any such write; tenant isolation of both new fields between two hospitals; `ehrWriteActivity` reflecting a real escalation-record write within the window; and the platform aggregate's new fields over HTTP. Full server suite: 160/161 passing — the one failure (`test/queue/queue.test.ts`'s stale-lock-recovery test) is a pre-existing, order-dependent flake in a file this fix didn't touch (passes in isolation; confirmed unrelated by running it standalone).
